# AR character Phase 1 — reproducible asset and capability audit

Date: 2026-10-22. Companion to [the implementation plan](../plans/2026-10-22-ar-character-presentation.md); the original checklist is deliberately unchanged.

**Outcome:** all seven GLBs and seven USDZs inspected, pinned SceneView 4.18.0 source inspected, Apple configuration paths checked. Physical-device baseline, runtime clip enumeration, visual quality, and sustained performance are **UNVERIFIED**. This is not Phase 1 device acceptance or a release sign-off.

## Reproduce

From the repository root (Python 3.9+; OpenUSD wheel availability depends on platform):

```sh
python3 -m venv /path/outside/repo/ar-audit-venv
/path/outside/repo/ar-audit-venv/bin/pip install -r tools/ar-audit-requirements.txt
/path/outside/repo/ar-audit-venv/bin/python tools/ar_asset_audit.py --output docs/superpowers/audits/2026-10-22-ar-assets.json
/path/outside/repo/ar-audit-venv/bin/python tools/ar_asset_audit.py --check docs/superpowers/audits/2026-10-22-ar-assets.json
/path/outside/repo/ar-audit-venv/bin/python -m unittest discover -s tools -p 'ar*_test.py' -v
python3 tools/ar_capability_audit.py --output docs/superpowers/audits/2026-10-22-ar-capabilities.json
```

The asset audit is offline/read-only except its explicit output. It reads GLB accessors (offsets, strides, sparse overrides, normalization), actual vertex and animation values, PNG headers, ZIP members, and composed USD data with OpenUSD 26.8. It does not treat binary string matches or ZIP filenames as animation inspection. Unsupported compressed accessor data fails explicitly. The capability audit downloads immutable-version Maven source JARs plus live Apple DocC JSON, recording SHA-256, source line evidence and unavailable HTTP results. It does not change dependencies or download into application folders. Apple live documentation can change; review regenerated diffs.

Generated evidence:

- [Asset inventory](2026-10-22-ar-assets.json): hashes, sizes, full GLB node/skin hierarchy, USD joint paths/names and transforms, all clip durations, root channel samples summarized as ranges/end deltas, primitive bounds, morph targets, textures, materials and shader connections.
- [Capability source evidence](2026-10-22-ar-capabilities.json): exact pinned source artifacts and Apple documentation excerpts. Line numbers below refer to those source JARs, not a moving GitHub branch.
- Tests assert asset pairing, unique/existing `Idle` mappings, absence of morph targets, single USDZ animations, cross-format default-geometry and Idle root-translation range parity, decoder behavior, and parsed-JSON-equivalent report regeneration. They do **not** prove semantic equivalence of every animated joint or renderer output.

### Rig, materials and textures

- All six dolls: one skin, 20 joints; `Bip001` → pelvis → spine/spine1/neck/head; clavicle/upper-arm/forearm/hand chains; thigh/calf/foot chains. No jaw, lip, tongue, finger or facial joints. Three mesh primitives/materials; no morph targets or USD blend shapes.
- Scan-any-page: one `AnimalArmature` skin, 51 joints, including Body/Back/Torso, neck/head, ears, tail, legs, pole targets and IK helper roots. No authored jaw/viseme rig or morph targets. Full hierarchy is in the JSON; do not mistake helper-root translation for whole-character locomotion.
- Dolls: Body base color PNG 2048×2048, Mouth 512×256, Eye 512×512. All six variants carry the same image dimensions and compressed byte counts. GLB Body is opaque; mouth/eyes use `BLEND`. Metallic = 0; roughness Body ≈0.328809, mouth/eyes ≈0.450054. `doubleSided` absent means glTF default false. USD PreviewSurface exports retain matching roughness/metallic, use sRGB diffuse textures and opacity texture connections for mouth/eyes. Runtime alpha sorting, premultiplication, mipmaps, color response and shimmer remain unverified.
- Scan-any-page: five double-sided, opaque, flat-color materials (`Main`, `Black`, `Eyes`, `Main_Light`, `Grey`), metallic 0, roughness 0.5; no image textures in either format. These are not equivalent material pipelines even where factors agree (Filament glTF PBR versus RealityKit USD import).
- Existing `ASSET_LICENSE.md` files remain authoritative provenance; no files or clips were trimmed/re-exported.

**USDZ parity limitation:** every doll has exactly one composed `SkelAnim` at `/<stem>/DollBody/skeleton__0_SkelRoot/skeleton__0/SkelAnim`, with 500 samples from 0 to 16.6333332 time codes at 1 time code/second. Scan-any-page has one at `/scan_any_page_character/AnimalArmature/AnimalArmature_SkelRoot/AnimalArmature/SkelAnim`, 101 samples from 0 to 3.33333325. There are no alternative animation variant sets in the composed hierarchy. These durations and audited root-translation ranges agree with GLB `Idle`; this is not evidence that USDZ contains `Happy`, `HappyIdle`, or any other named GLB clip. USD custom data has an empty `defaultAnimationTrack`, not an `Idle` name contract. RealityKit's runtime `availableAnimations` names, recursive entity ownership and playback behavior must be enumerated on-device; `SkelAnim` is a USD prim name, not a guaranteed RealityKit lookup string.

Recommended mappings for **each** `cute_doll_v01`–`cute_doll_v06` and `scan_any_page_character`:

| State | GLB contract | Current USDZ contract |
|---|---|---|
| Idle | exact `Idle` | single baked Idle-like resource only after runtime enumeration/validation; otherwise stable pose |
| Paused | hold a stable pose or deliberately use `Idle` | stable pose; no artificial whole-entity bob |
| Speaking | **no dedicated clip verified**; retain idle until a gesture is visually approved/authored | no separate speaking resource verified |
| Completion | optional, no default mapping approved | unavailable as a distinct authored clip |

`HappyIdle`, `Happy`, `Reaction`, and `Idle_2` are inspection candidates, **not approved speech clips**. Do not map combat/death/hit/locomotion clips, `ZZ_ALLAnim`, or clip order to narration. There are no authored phoneme/viseme channels to support true mouth synchronization.

### Root motion and facing evidence

Doll `Bip001` local translation ranges, shared by all variants:

| Clip | Key range span X/Y/Z in source units | End-minus-start significance |
|---|---|---|
| `Idle` | 0.053840 / 0.011666 / 0.018735 | each component <0.000001 |
| `HappyIdle` | 0.012772 / 0.019596 / 0.020623 | each component <0.000004 |
| `Happy` | 0.100508 / 0.004378 / 0.017572 | max absolute component ≈0.000353 |
| `Reaction` | 0.032712 / 0.011214 / 0.029359 | zero at sampled endpoints |

Scan-any-page `Idle` Body span ≈0 / 0.017637 / 0.008818 with matching endpoints. It also has multiple IK/helper root channels. Full root/ancestor translation, rotation and scale ranges for **every clip** are in the JSON. These sampled local-space values establish bounded root-channel excursions, **not** zero world drift, planted feet, safe transitions, or a subtle/appropriate gesture. Rotation and all bone deformations can move the visible body even when root endpoints match. Interpolation extrema, animated skinned bounds, foot sliding, loop seams, crossfades and cumulative playback behavior need rendering checks.

**Forward-axis candidate: +Z for all seven stems in both formats.** Evidence: doll Eye/Mouth vertices are around Z +0.40/+0.41 while the body mean is around −0.02; scan-any-page Eyes are around Z +2.20, black nose-like geometry around +2.66. USD primitives retain the same geometry/bounds/means. This is geometric inference, **not a declared glTF/USD forward-axis metadata field or device-verified facing**. Confirm the front visually before making it a production contract.

For a wrapper whose local front is +Z, candidate yaw is `atan2(camera.x - anchor.x, camera.z - anchor.z)`, about +Y in a right-handed world, with zero extra asset yaw. If the native “look at” helper points local −Z at its target, add π or use a +Z-aware helper; do not apply both corrections. Ignore camera/anchor Y when facing. Test each format at camera positions +Z, −Z, +X and −X, then orbit after placement: the character must face the initial viewer but remain anchored, not continually turn toward the camera. Animated pose offsets may rotate the face relative to the wrapper.

## Explicit capability matrix

Status meanings: **source-confirmed** = implementation/API contract inspected; **baseline code** = source seen before parallel native changes; **unverified** = not measured on a physical device. Source support does not equal enabled, useful, or performant.

| Capability | Android / SceneView 4.18.0 | iOS / RealityKit + ARKit | Runtime status / action |
|---|---|---|---|
| Automatic animation | `ModelNode.kt:282–284` starts **every** animation when `autoAnimate=true`; `playAnimation(name)` exists (`338–340`). All active animations are applied by the animator, not a semantic idle selector. | Baseline reader looped first `availableAnimations`; runtime resource names are not established by USD metadata. | Source-confirmed; disable generic autoplay and enumerate/select deliberately. Actual playback unverified. |
| Environment lighting | `LightEstimator.kt:96` enabled by default. `ARScene.kt:930` presets HDR, then application callback can override. `1424+` consumes estimate into main light and environment IBL. Baseline app overrode to `AMBIENT_INTENSITY`; estimates were **not necessarily unused**. | Baseline reader explicitly requested `.automatic` environment texturing. Room-dependent lighting/material response is not established here. | Source-confirmed supported Android HDR path; confirm effective mode and estimate validity on device. No dependency upgrade required by this finding. |
| Grounding shadows | `SceneFactories.kt` enables main-light shadows. `PlaneRenderer.kt:141` defaults shadow receiver true. But `ARScene.kt:1209` assigns `planeRenderer` to **isEnabled**; `PlaneVisualizer.kt:145` removes the whole renderable when disabled. Baseline `planeRenderer = !placed` therefore disables that receiver after placement, not merely grid visibility. | Apple documents built-in grounding AO/shadows and `renderOptions.insert(.disableGroundingShadows)` to disable them; absence of custom receiver does **not** establish absent shadows. | API/source-confirmed. Verify on physical surfaces before adding a second shadow. Android should decouple grid visibility from receiver or supply an intentional receiver. |
| Depth/room occlusion | `ARScene.kt:421` defaults depth mode `DISABLED`; `ARCameraStream.kt:322` defaults `isDepthOcclusionEnabled=false`. Depth-aware material path exists. Request supported depth mode **and** renderer occlusion; grouped `SceneUnderstanding` can set the latter. | Scene reconstruction defaults `.none` in ARKit SDK header; available from iOS 13.4, requires `supportsSceneReconstruction(.mesh)` (LiDAR-capable supported device) and RealityKit scene-understanding `.occlusion` to use reconstructed geometry as an occluding depth buffer. | No claim of enabled occlusion in baseline. Query and log actual support/configuration separately; edge quality and cost unverified. |
| People occlusion | Do not equate ARCore environment depth with a verified person/hand segmentation solution. SceneView has additional person-occlusion facilities, not enabled or evaluated by this audit. | Apple `disablePersonOcclusion` docs describe default person occlusion. Separately, manually created ARKit configurations default `frameSemantics` to none. Check `ARWorldTrackingConfiguration.supportsFrameSemantics(.personSegmentationWithDepth)` and effective running configuration; explicitly request supported semantics when owning the session. | Default render feature ≠ proven data available. Baseline enabled semantics and actual people/hand occlusion **unverified**, not “definitely missing” or “definitely enabled.” |
| Anchor disposal | `ARSceneScope.AnchorNode` uses `NodeLifecycle`; `SceneScope.kt:1718–1723` detaches/destroys on disposal; `AnchorNode.destroy()` detaches ARCore anchor; replacing `anchor` also detaches old anchor. | Use session ARAnchor lifecycle appropriate to committed placement; no leak claim established by this audit. | Android library ownership source-confirmed. Application cancellation/replacement cycles and memory growth unverified; avoid disposing an anchor intended to survive Move/Cancel. |
| Model loading thread | `utils/File.kt` uses `Dispatchers.IO` for file loading; suspend `loadModel()` explicitly invokes `assetLoader.createAsset` on `Dispatchers.Main`, then suspended resource loading. `loadModelInstance()` delegates to it. | Baseline used asynchronous Entity loading; no timing measurements here. | “All file read and parse off main” is inaccurate for Android. Keep Filament thread-affine calls on supported path; profile cold-load stalls rather than wrapping arbitrary calls in IO. |
| Kotlin/renderer pin | Inspected **4.18.0** source, not latest HEAD; no application dependency changes. | Project deployment target inspected as iOS 13.0; reconstruction must be availability- and device-gated. | Existing compatibility pin retained. No native build was run for this documentation/tooling change. |

- Use a monotonic timestamp at native reader presentation as t0. Camera-ready = first rendered camera frame, not permission callback or session creation. Model-ready = loaded instance ready for scene attachment; valid-placement = first current center hit passing tracking/upward-plane eligibility; confirmed-placement = user confirmation. Record separately: human scanning time is not model-load latency. Report instrumentation unavailable as null, not inferred from a loading label.
- Five cold reader opens (declare process/asset-cache conditions) and five warm opens per configuration; report per-run data plus median/range. Keep permission prompts out of steady-state timing or label first-install separately. Do not claim OS file caches were purged unless they were.
- Frame pacing: device profile/release build, Android Perfetto/FrameTimeline plus renderer traces as available; iOS Instruments animation/game performance/Metal tools as available. - Memory: Android PSS via `dumpsys meminfo` or profiler; iOS physical footprint via Instruments. Label metric and sampling interval; they are not directly comparable. Capture after load, after placement, each minute, peak and after close/reopen cycles. Log Android thermal service/thermal status and iOS `ProcessInfo.thermalState`, battery/charging state. No fabricated temperature readings on devices without a sensor/API.

### Fixed 15-minute reading run

1. Set brightness and table/camera distance consistently; document chosen values. Use the same story/audio and network/cache conditions. Start on a textured horizontal table in bright indirect light. Record pre-run thermals and memory; log effective capabilities and loaded animations.
2. **0–2 min:** enter reader, scan slowly, wait for current-center ready state, place at approximately 0.5 m camera distance. Verify initial facing, true foot contact, material/alpha quality and single grounding shadow. Orbit to four sides without moving the committed anchor.
3. **2–5 min:** narrate multiple consecutive clips/pages, Pause/Resume and Back/Next. Confirm no idle flash between audio clips, no unrelated combat/locomotion clips, no root accumulation, no story/progress reset. Observe a full Idle loop (including doll's 16.63 s loop).
4. **5–8 min:** ten Move→Cancel and ten Move→Confirm cycles. Confirm retained old placement until confirmation, no overlapping characters or leaked anchors, preserved audio offset, explicit-only resume. Record whether controls remain reachable on compact portrait layout and larger text settings in a separate visual run.
5. **8–11 min:** pass a book edge, cup, moving hand and person in front; compare depth enabled/disabled with matched camera/table positions. Repeat on a plain table and under warm/dim light in separate matched runs. Note invalid depth, flicker, holes and small-object misses separately from support flags.
6. **11–13 min:** cover camera briefly, move rapidly, look away and back, background for 15 s and return. Record tracking recovery, anchor movement and audio state; never count intentional duplicate placement as recovery. Repeat interruption/failure cases safely where possible.
7. **13–15 min:** continue narration without interaction. Record end frame pacing/memory/thermal state, then close/open reader ten times and compare retained memory/anchor behavior after a consistent settling interval. Distinguish cache warm-up from continuing resource growth.

Run baseline first, then one effect change at a time (HDR, grounding, scene depth, people semantics) and finally the proposed combined tier. Use the same device/lighting and cool-down state; repeat at least three sustained runs before choosing budgets. Budgets and acceptable regressions are **TBD from measured baseline**, not assigned by this audit. Keep a complete no-depth reading path.
