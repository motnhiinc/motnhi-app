Interactive Storybook Voice + AR App — High-Level System Architecture

Mobile client, 9 backend API services, 6 async workers, and shared data layer (spec sections 9.1, 9.2, 9.5, 11, 18)

Thin client, signed-URL assets

  • • Five modules: Child Story Player, AR Module, Audio Playback Engine, Offline Cache, Parent Dashboard (Flutter/RN + Unity/native AR, §9.2).
  • • API services return signed URLs; the client downloads audio + AR bundles directly from the CDN, never streamed by the API.
  • • Offline Cache (SQLite/Drift/Hive) holds cached audio, AR assets, and page metadata for offline playback.

9 read-mostly API services

  • • Auth, Child Profile, Story Content, Audio Asset, AR Asset, Story Session, Entitlement, Analytics, Admin/Publisher (§9.5).
  • • All read/write PostgreSQL; Story Content and Story Session lean on Redis for hot responses and resume state.
  • • Admin/Publisher enqueues the heavy lifting onto async workers rather than doing it inline.

Workers + shared data layer

  • • 6 queue-driven workers (Voice Gen, Audio Proc, AR Asset, Image Target, Safety Review, Recommendation) write assets to Object Storage and update status in PostgreSQL.
  • • Data layer: PostgreSQL (record), Redis (cache), Analytics Warehouse, Object Storage, CDN (origin → edge).
  • • All child-facing assets are pre-generated and human-reviewed before publish (§18.2, §13.2).

AR Recognition & Scene Pipeline

Reference-image detection to 2D scene render (MVP on-device, spec 9.3 / 11.5)

Server-Side Production

  • • Book page art passes an image-quality validation gate before any reference-image DB is built — poor source images are rejected early.
  • • The Image Target Worker builds the reference-image feature DB and the per-story image-target manifest asynchronously.
  • • AR Asset Service maps page_id to scene_json and manages asset-bundle versions; Object Storage and CDN front the finished assets.

Manifest Handoff

  • • The CDN-delivered image-target manifest plus asset bundle is the single handoff from production to device (GET /v1/stories/{id}/image-target-manifest, 11.5).
  • • Object Storage is the origin; the CDN serves the bundle at the edge for low-latency, offline-tolerant downloads.
  • • AR Asset Service version control prevents manifest-vs-cached-bundle skew.

On-Device AR (MVP)

  • • Detection runs on-device from the downloaded target DB: camera detects target, resolves page_id, loads scene_json, renders the 2D character.
  • • A tap triggers play_audio_segment, fetching the linked audio from the CDN — the only live server call in the device loop.
  • • Server recognition is fallback/update only; this keeps AR page detection under the <2 s target (17).

Voice & Audio Pipeline

Offline production (pre-generate + review) and on-device playback of approved audio assets

Offline production, never real-time

  • • Manuscript flows through text cleaning, page segmentation, and character detect/assign into a structured narration script (speaker, voice_id, emotion, speed, timing).
  • • The Voice Generation Worker is the only component that calls the External TTS API; Audio Processing handles normalization and SFX/music mixing.
  • • §18.2 mandates pre-generate + cache narration and avoid real-time TTS for child sessions.

AI safety gate before lock

  • • Mixed audio draft passes policy filters, then an age-appropriateness classifier, then the Safety Review Worker queue.
  • • Human Editorial Review is the binding approval gate — only on approve do assets become version-locked.
  • • Locked assets are then published to Object Storage; nothing unreviewed ever reaches the child app (§13.2, §27.4).

Signed-URL playback on device

  • • Object Storage distributes to CDN and registers signed URLs + versions with the Audio Asset Service.
  • • Playback Engine GETs the narration script from Story Content Service and exchanges signed URLs with Audio Asset Service.
  • • Approved audio streams from CDN; the Offline Cache holds downloaded audio + metadata for gapless, bedtime, offline playback.

Content Production & Publishing Flow

Publishing state machine, human gates, and AI-gated content for the child app (spec §7.3, §8, §12, §13.2, §19)

Human-gated state machine

  • • Draft → Internal Review → Safety Review → Device QA → Published → Archived; no state advances without a human approval.
  • • Safety Review enforces an 11-point child-safety checklist before content can reach Device QA.
  • • Device QA deploys to Staging; only Published locks and promotes to Production for the child app.

Roles, least-privilege & audit

  • • Six scoped admin roles (Editor, Audio, AR, Safety, Publisher, System) — each touches only its stage.
  • • System Admin owns RBAC + MFA; Publisher Admin gets read-only reports, never edit rights.
  • • AI drafts pass Policy + Age gates into Content Studio — never directly into the child app; every action hits the Audit Trail.

Rights, entitlement & delivery

  • • Rights Mgmt attaches licenses, scopes campaigns to Entitlement Svc, and auto-disables expired content (→ Archived).
  • • Production serves approved assets to the Child App over signed URLs.
  • • Entitlement / Activation Svc handles redeem-code → unlock so codes gate access to delivered content.
